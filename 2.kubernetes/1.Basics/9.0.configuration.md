## **Kubernetes Configuration (YAML)**

Kubernetes uses **YAML files** to define and manage resources such as Pods, Deployments, Services, ConfigMaps, and Secrets.

### **Why do we need YAML configuration?**

- Define Kubernetes resources declaratively.
- Maintain configurations as code.
- Easily deploy and update applications.
- Reuse configurations across different environments.

### **Basic YAML Structure**

Example: Kubernetes Pod configuration.

```
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  labels:
    app: my-app
spec:
  containers:
    - name: my-container
      image: nginx
      ports:
        - containerPort: 80
```

### **Important YAML Fields**

| Field      | Purpose                                                       |
| ---------- | ------------------------------------------------------------- |
| apiVersion | Specifies the Kubernetes API version.                         |
| kind       | Specifies the resource type (Pod, Service, Deployment, etc.). |
| metadata   | Contains resource information such as name and labels.        |
| spec       | Defines the desired configuration of the resource.            |
| containers | Defines containers running inside the Pod.                    |
| image      | Specifies the container image.                                |
| ports      | Specifies the container ports.                                |

### **How to Apply YAML Configuration?**

```
kubectl apply -f pod.yaml
```

Other useful commands:

```
kubectl get pods
kubectl describe pod my-pod
kubectl delete -f pod.yaml
```

**In simple words:** Kubernetes YAML files define what resources we need and how they should run. Kubernetes uses these configurations to create and manage resources.

## **3 Main Parts of Kubernetes Configuration (YAML)**

Every Kubernetes configuration file mainly contains three sections:

### **1. apiVersion**

Specifies which Kubernetes API version is used to create the resource.

Example: `v1`, `apps/v1`

### **2. kind**

Specifies the type of Kubernetes resource we want to create.

Examples: `Pod`, `Deployment`, `Service`, `ConfigMap`.

### **3. metadata**

Contains information about the resource, such as:

- name
- labels
- namespace

### **Example**

```
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  labels:
    app: my-app
spec:
  containers:
    - name: nginx
      image: nginx
```

**Note:** The above file also contains `spec`, which defines the desired configuration of the resource.

**Remember:**

- apiVersion → Which API version?
- kind → What resource?
- metadata → Resource information.
- spec → How should the resource be configured?

## **Status in Kubernetes Configuration**

**Status** represents the current state of a Kubernetes resource.

- It is maintained and updated by Kubernetes.
- Shows the actual state of the resource.
- Helps identify whether the resource is running successfully or has errors.
- Generally, we don't manually configure `status` in YAML files.

### **Example**

```
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
    - name: nginx
      image: nginx
```

After creating the Pod, Kubernetes maintains its status.

Common Pod statuses:

| Status    | Meaning                                             |
| --------- | --------------------------------------------------- |
| Pending   | Pod is waiting to be scheduled or started.          |
| Running   | Pod is running.                                     |
| Succeeded | All containers completed successfully.              |
| Failed    | All containers terminated, and at least one failed. |
| Unknown   | Pod state cannot be determined.                     |

**Remember:**

- `spec` → Desired state (what we want).
- `status` → Actual state (what is happening).

## **Self-Healing in Kubernetes Based on Status**

Kubernetes uses **Controllers** to continuously compare the desired state (`spec`) with the actual state (`status`).

If they don't match, Kubernetes takes corrective action automatically.

### **Example**

Suppose a Deployment requires 3 Pods.

1. **Desired State:** 3 Pods (`spec.replicas: 3`).
2. **Actual State:** Only 2 Pods are running.
3. **Detection:** Controller Manager detects the mismatch.
4. **Action:** ReplicaSet Controller creates another Pod.
5. **Result:** Kubernetes restores 3 running Pods.

### **Other Examples**

- Container crashes → Kubelet restarts it (based on its restart policy).
- Pod gets deleted → ReplicaSet creates a replacement.
- Node fails → Kubernetes can reschedule Pods onto healthy nodes, depending on configuration.

**In simple words:** Kubernetes continuously monitors the actual state against the desired state and automatically takes action to maintain the desired state. This is called **Self-Healing**.

## **Kubernetes Configuration Files – Formats and Storage**

### **1. File Formats**

Kubernetes supports the following formats for configuration files:

- **YAML (**`.yaml`**&#x20;/&#x20;**`.yml`**)** – Most commonly used.
- **JSON (**`.json`**)** – Also supported.

Example filenames:

- `pod.yaml`
- `deployment.yaml`
- `service.yaml`
- `configmap.yaml`

### **2. Where to Store Configuration Files?**

Kubernetes configuration files are generally stored in your application project's repository, managed using Git.

Example project structure:

```
my-project/
│
├── src/
├── Dockerfile
├── pom.xml
│
└── kubernetes/
    ├── pod.yaml
    ├── deployment.yaml
    ├── service.yaml
    ├── configmap.yaml
    └── secret.yaml
```

### **3. How to Apply Configuration?**

Use `kubectl` to apply YAML or JSON files to the Kubernetes cluster.

```
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
```

To apply all files inside a directory:

```
kubectl apply -f kubernetes/
```

### **Remember**

- Format → YAML or JSON.
- Storage → Usually inside the project's Git repository.
- Deployment → Use `kubectl apply -f`.
- Kubernetes stores the resulting resource state in `etcd`.

**In simple words:** We write Kubernetes configurations in YAML/JSON, maintain them in our project repository, and apply them to the cluster using `kubectl`.
